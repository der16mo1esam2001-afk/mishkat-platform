## 2. الضوابط الأمنية المحققة والمثبتة برمجياً

1. **عزل قواعد البيانات الخمس (Strict Multi-DB Isolation):**
   - فصل فيزيائي تام عبر 5 قواعد بيانات PostgreSQL مستقلة.
   - تفعيل `ENABLE ROW LEVEL SECURITY` و`FORCE ROW LEVEL SECURITY` على كافة الجداول المملوكة للمستخدم.
   - دوال الأمان في مخطط `app_private` مع صلاحيات تنفيذ مقصورة على دور التطبيق `mishkat_app`.
   - استخدام مفاتيح أجنبية مركبة تشمل `owner_id` (Composite Foreign Keys) لمنع ربط أي سجل فرعي بمالك آخر.

2. **الهوية والصلاحيات والتحكم في الوصول (RBAC & Identity):**
   - حظر مصادقة التطوير (`dev_auth`) تماماً عند ضبط `ENVIRONMENT=production`.
   - استخراج هوية المستخدم ومالك السجلات (`sub`) حصرياً من claims الموقعة داخل الرمز المصدق على الخادم.
   - إضافة أدوار محددة: `platform_admin`, `domain_operator`, `auditor`, `learner`, `authenticated`.

3. **حماية الـ API وشبكة الاتصال:**
   - طبقة تحديد معدل الطلبات (Sliding Window Rate Limiter) بمعدل 120-200 طلب/دقيقة للعنوان IP لمنع هجمات الحرمان من الخدمة وهجمات القوة الغاشمة.
   - ترويسات أمان متشددة: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`.
   - سياسة أمان محتوى صارمة (CSP) وHSTS مفعّلة في بيئة الإنتاج.
   - منع التخزين المؤقت لاستجابات الـ API: `Cache-Control: no-store, max-age=0` لمنع تسريب البيانات الحساسة عبر المتصفحات المشتركة.

4. **سلامة الذكاء الاصطناعي وبوابة النماذج (AI Gateway Security):**
   - مرشح آلي لاكتشاف حقن التوجيهات (Prompt Injection Defenses) والتجاوزات الأمنية (Jailbreaks).
   - رفض حازم لأي طلبات تشخيص سريري أو وصف علاجي مستقل بموجب سياسة السلامة الطبية لـ VITALIS.
   - رفض حازم لأي أوامر تحكم تشغيلية (صمامات، مضخات، قواطع شبكة) بموجب سياسة القراءة فقط لـ AQUANEX وENERGIS.
   - سجل أدوات محكوم (Tool Allowlist) مع اشتراط "معاينة الإجراء" وتوليد رمز موافقة بشري (Approval Token) قبل أي كتابة خارجية.

5. **تنقية السجلات والخصوصية (Logging Redaction & Privacy):**
   - تنقية آلية لكلمات المرور والمفاتيح ورموز Bearer في سجلات الخادم عبر `redact_sensitive_text`.
   - مسار حذف شامل (Right to be Forgotten) في مساحة NEXORA لتطهير البيانات نهائياً بناءً على طلب المتعلم.

## 3. الثغرات والملاحظات المفتوحة وخطة إغلاقها

### ملاحظة M-01 (متوسطة): غياب خادم JWKS إنتاجي حي في البيئة المحلية
- **الوصف:** وضع `supabase_jwks` مدعوم كودياً ومختبر بضوابط تحقق، لكنه يتطلب إعداد `SUPABASE_JWKS_URL` و`SUPABASE_ISSUER` حقيقيين في بيئة الاستضافة السحابية.
- **خطة الإغلاق:** يقوم مالك المنصة بربط مشروع Supabase أو خادم OIDC (مثل Keycloak أو Auth0) وتعيين المتغيرات في بيئة Staging.

### ملاحظة M-02 (متوسطة): حصر صلاحيات Docker في بيئة التشغيل المستقلة
- **الوصف:** نظراً لعدم توفر Docker CLI في محطة العمل الحالية، لم يتم اختبار تشغيل حاويات PostgreSQL الخمس محلياً عبر compose في هذه الجلسة.
- **خطة الإغلاق:** تشغيل `docker compose up -d` على بيئة تحتوي Docker واختبار الاتصال الشبكي المباشر بقواعد البيانات الخمس.

## 4. إقرار بوابات القبول الأمنية
اجتازت الحزمة بوابات القبول: لا توجد ثغرات حرجة أو عالية، لا توجد أسرار مكشوفة في المستودع، ولا توجد ادعاءات غير قابلة للإثبات.
